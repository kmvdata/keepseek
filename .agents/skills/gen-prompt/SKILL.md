# gen-prompt（生成可投喂的开发 Prompt）

把本 Skill 作为"将非正式用户需求整理成可交接给全新 AI session 的完整开发 prompt"的唯一入口。它是一个**元技能**：先透彻理解需求，再产出一份自包含、带架构约束与验收标准的 prompt 文本，交给用户复制到新 session 独立执行。

本 Skill **不绑定任何具体项目、语言、框架或技能体系**，提炼的是"需求 → 可执行 prompt"的通用方法论。项目相关的约束必须在产出时从目标项目实际情况中提炼，而不是照搬本 Skill 所在项目的约定。

不要在解释、评审或实际编辑代码时只使用本 Skill——那种情况应直接使用对应的开发技能。

## 触发判定（先看这里）

命中任意一条**强信号**即可触发本 Skill；只命中**中信号**时结合当前请求判定；属于**不触发**场景时不要使用。

### 强信号（命中即用）

- 用户要求"生成 / 写 / 整理 / 完善一份 **prompt / 提示词 / 开发任务说明 / 需求文档**"。
- 用户要求把需求"**整理成可交接（handoff）**给全新 AI 会话的完整开发 prompt"。
- 用户提到"**新 session / 新会话 / 全新 AI / 从头开始执行**"，且目标是产出一份可直接投喂的任务文本。
- 用户要求"**不依赖当前项目 / 当前上下文 / 本仓库 Skill** 的自包含 prompt"。
- 用户说"把这段讨论 / 这个需求 **整理成可执行的开发指令**"。

### 中信号（结合上下文判定）

- 需求描述较模糊，且用户明确表示"先整理成任务文本、之后再执行"。
- 用户期望的交付物是**可复制的文本**（粘贴到别处执行），而不是本会话内的代码改动。

### 不触发（不要用本 Skill）

- 用户直接要求修改 / 实现 / 评审 / 解释代码：使用对应的开发技能或正常对话。
- 用户描述需求并期望**直接开始开发**：不要绕到 prompt 生成。
- 用户显式指定了其他 Skill：遵循显式选择。

## 使用协议

1. **理解需求**：按下方"输入采集"清单向用户澄清目标、边界、涉及层/域、数据资源、契约与验证要求；信息不足但可合理推进时，按惯例补全，并在 prompt 中标注假设，不凭空捏造细节。
2. **提炼约束**：识别目标项目真实存在的架构 / 分层 / 契约 / 流程约束（从项目文档、已有实现或用户提供的信息中提炼），写成具体条款，不发明不存在的规则。
3. **组织结构**：按"背景与目标 → 范围与不做 → 架构 / 分层约束 → 数据与契约 → 实现要求 → 验证清单 → 交付与验收"组织产出，把采集到的要点与约束写成**具体可执行的话**，做到目标 session 即使不读取任何原始 skill 或文档也能按规范开发。
4. **产出前检查**：结构完整（未命中的 section 标注"不适用"）、占位符已清除、红线与验证步骤没有丢、没有把"请阅读某文件/某 skill"当成规范内容本身。
5. **交付**：把最终 prompt 作为交付物呈现给用户，并附投喂方式与建议补充的上下文。

## 输入采集（先弄清这些）

| 问题 | 说明 |
|---|---|
| 功能目标 | 要做什么、解决什么问题、范围边界？改动属于聊天 UI / Agent 运行 / 上下文引用 / 编辑管线 / Skill 机制中的哪一块？ |
| 涉及模块 | 改动落在哪些层：`extension.ts`（激活/命令）、`provider/`（消息接线）、`agent/`（编排/工具/协议/压缩）、`webview/`（模板/样式/脚本/输入区）、`sessions/`、`context/`（上下文文件与引用）、`edits/`（ChangeSet/DraftEdit）、`skills/`、`shared/`（config/i18n）？列出具体文件。 |
| 协议与消息 | 是否新增/修改 `provider/webviewMessages.ts` 的消息类型或主动推送消息？webview 的 DOM id、message type、序列化格式是否要求兼容？ |
| 持久化与配置 | 是否涉及会话存储（`keepseek.chatSessions`）、ChangeSet 持久化、`shared/config.ts` 的 keepseek.* 配置项？旧数据是否需要兼容或迁移？ |
| 上下文与引用 | 是否影响 @ 文件/目录引用、$ Skill 引用、选区引用、`FileContextStore` 或引用展开授权？ |
| 工具与安全 | 是否新增/修改 agent 工具（workspace / semantic / validation / git）或 `toolAuthorization.ts` 授权分级？是否涉及 DraftEdit / 删除授权 / 脏编辑器保护 / checkpoint 回滚？ |
| 验证要求 | keepseek 真实检查命令：`npm run compile`、`npm run lint`、`npm run build:test`、`npm test`；发布前 `npm run package`（校验运行时依赖与 main，禁止绕过）。 |

采集不足但可合理推进时，按 keepseek 现有实现惯例补全，并在 prompt 中明确提示目标 session 先阅读相关源码（如 `provider/`、`agent/`、`webview/` 对应模块），不凭空假设消息类型、存储格式或工具行为。

## 产出质量标准

- **自包含**：目标 session 不依赖当前对话上下文即可独立执行；把必要规范写成具体句子内嵌在 prompt 中。
- **有边界**：明确开始步骤（先读真实代码/文档）与结束条件（验收标准 / DoD）。
- **有红线**：把目标项目实际的分层、隔离、契约、多语言、不降级等硬约束写成禁止/必须条款。
- **可验证**：列出适用的检查命令与通过标准。
- **无泄漏**：明确写出"不做 / 不属于本需求"的项，防止顺手重写无关代码。
- **纯净高效**：只保留对新 session 执行有指导价值的内容；不掺入本 Skill 所在项目的历史上下文或无关细节。

## 交付物

输出一份可直接粘贴到新 AI session 的完整 Markdown prompt（按"使用协议"第 3 步的结构组织的最终文本），并简要说明：
- 这份 prompt 覆盖了哪些关键约束；
- 目标 session 建议补充哪些上下文（如仓库路径、已确认的契约与决策）；
- 建议的投喂顺序与注意点。
