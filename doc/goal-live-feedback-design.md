# Goal 准备与 Agent 实时反馈设计

## 问题与目标

Goal 模式提交后不能只在底部状态栏显示“正在生成 Goal 提案”。准备过程必须成为一个始终可见、可取消、可恢复的界面状态；Agent 启动后，正文、推理、阶段切换、工具活动、等待和失败也应在对话列表中得到适合的反馈。

本改进遵守三个边界：

- Extension Host 是 Goal、提案和运行状态的唯一权威；Webview 的乐观状态只用于消除首帧空白。
- Goal 准备状态与 Agent 活动是 view-only 投影，不写入 `ChatSession.messages`，也不进入 Provider replay。
- 不把原始 SSE、提案 JSON、工具参数、凭据或隐藏推理直接展示给用户；只展示安全的正文/已支持的推理流和宿主归一化活动。

## 交互需求

### Goal 提案准备

1. 用户提交 Goal 后，同一帧显示持久准备卡，包含目标摘要、当前阶段、模型、流式接收进度和操作。
2. 准备阶段至少区分：校验目标、解析模型、等待模型、接收提案流、完成、失败、取消。
3. 生成期间必须提供“取消生成”和“放弃提案”入口；取消后保留安全的保守提案（若可生成），并允许重新生成或按原目标创建。
4. 即使保守提案尚未形成或输入校验失败，也必须显示错误卡和恢复操作，不能只剩状态栏，也不能永久停留在“生成中”。
5. 提案生成成功后，原位切换为确认卡；选项、依赖关系、范围和预算仍由用户确认后才创建 Goal。

### Agent 实时反馈

1. 正文和受支持的推理增量继续进入当前 assistant 消息。
2. 对话列表底部增加 view-only 实时活动面板，最多保留最近 8 个状态、显示最近 5 个，覆盖上下文准备、模型等待、推理、生成、工具、验证、审批等待和收尾。
3. 活动变化应随 `agentRunDelta` 与宿主状态修订即时刷新；切换会话或开始新一轮运行时清空，避免串线。
4. 活动面板不修改消息数组；运行结束后由最终 assistant 消息、Run Details、ChangeSet、DraftRun 或 Goal 状态卡承接结果。
5. 动画遵守 `prefers-reduced-motion`，窄侧栏允许文案换行，不遮挡操作。

## 状态与故障恢复

Goal 准备状态由宿主投影 `generationStatus + preparationStage + generationMessage + streamedCharacters`。Webview 提交时先创建仅用于展示的占位状态，下一次单调递增的宿主 revision 会整体替换它。

所有初始校验均在可见状态建立后执行。校验、模型解析、网络、流解析或严格提案解析任一步失败，都进入 `error`，显示经过脱敏的原因以及“重新生成 / 放弃”操作。取消进入 `cancelled`，AbortController 与 generation fencing 保证迟到结果不能覆盖取消状态。

## 验收标准

- 提交 Goal 后无需等待宿主网络请求即可看到准备卡和取消按钮。
- 无提案、非法目标、模型不可用、超时、返回无效 JSON、主动取消均不会形成无操作的“生成中”死状态。
- 提案流开始后，卡片显示接收阶段和累计字符数，但不显示原始 JSON。
- Agent 运行时，正文/推理仍流式更新，阶段与工具活动同时出现在对话列表的实时活动面板。
- 实时 UI 数据不写入普通聊天历史或 Provider replay，不改变 V1–V10 请求前缀与工具 schema。
- Webview 脚本可解析，TypeScript 编译、lint 与现有测试全部通过。
