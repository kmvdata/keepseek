# KeepSeek 全自动审批验收

> 历史报告：2026-11-05 起的当前合同与现场步骤见 [帮我审批统一验收](keepseek-approve-for-me-verification.md)。当前仅 ask / delegate 两模式；旧版“全程不转人工”及独立 model_review 合同已被替代。以下内容保留原版本验收背景，不作为当前功能说明。

基线为 `8148abe`。在可信工作区选择「自动审批」后，当前任务的审批、执行结果交接和受支持的续跑由宿主推进。项目代码、工具和模型属于该模式的信任范围。宿主进程可以写入和清理项目、运行脚本及安装依赖。进程使用 VS Code 扩展宿主账号的真实权限，可能访问项目外资源。审批记录中的启动指纹、过滤环境和一次性许可约束本次授权，操作系统隔离另记为 `none`。可见目标检查可以阻止明确的越权行为，复杂动态代码的传递效果由项目级信任和专用 reviewer 评估。

## 人工入口与改后行为

| 入口 | 旧触发条件 | 自动审批现在的行为与验收 |
| --- | --- | --- |
| DraftEdit、ChangeSet、SafeFileEditor | 写入、移动、删除、外部路径、编辑器状态变化 | 保留原子写入、基线与脏编辑器检查。范围明确的项目编辑直批，其余可审查操作送专用 reviewer。外部写入需要事先绑定的精确写授权，引用的读授权不适用。缺权时自动尝试已有授权的替代路径，未执行的草稿结束。 |
| DraftRun、Scope、Store、Executor | Git 参数未覆盖、动态命令、外部路径或启动配置变化 | 先查硬边界和实际启动身份，再直批或送审。执行前比对不可变草稿、精确范围、启动身份和配置，消费持久化记录并签发单次 permit。Executor 采用已核实的 launcher、cwd 和环境，以 `shell:false` 启动。 |
| 固定验证与外部读取 | 证据不足、模型拒绝或未预授予外部引用 | 固定验证仅使用已注册的 compile、lint、test。启动快照变化会重新审查。失败按实际结果交回任务，关闭手工验证回调。已授权的外部读仅向 reviewer 提供目标元数据。 |
| Git 和批次依赖 | 首个命令受阻，后续批次等待用户 | 保留依赖顺序。可证明独立的本地无可选锁状态查询可核对当前仓库。依赖不明确的草稿结束，附具体前置操作和原因。预检修正和可执行替代路径共享有限的任务预算。 |
| 审批恢复、旧记录和 Webview 消息 | 重启后曾提供授权、确认、重试或恢复按钮 | 旧自动审批等待记录转换为终态并保留审计和修正诊断。重启不会恢复队列或 permit。缺少本次运行授权的旧草稿不会自动重放。宿主拒绝伪造的确认、授权、验证决定和旧计划启动消息。 |
| Plan、后台验证和子代理 | 执行计划按钮或后台验证应用后手动续跑 | 明确的只做计划请求在计划交付后结束。已选 Plan 时，识别到明确执行请求可直接进入执行。后台验证以同一任务及原有预算接续已处理的审批。子代理角色仍只能按原权限读取或提案。 |
| ask 与 model_review | 用户点击或模型审批自己的 reviewer | 保留各自的既有交互和模型配置。自动审批专用 reviewer 默认跟随主模型，也支持独立固定配置，记录、配置绑定和熔断按角色分开。 |

Git 直批验证覆盖 `git tag --list --sort=-v:refname` 和 `git log --oneline --decorate -n 80`。Git 的配置重定向、外部 helper、签名和引用修改继续通过对应检查。可验证的本地标签或分支创建使用实际仓库，删除或强制更新已有引用送审。远端 push、部署及独立外部网络操作当前缺少供本模式使用的精确远端目标授予入口，相关路径结束。已有精确文件与工作目录授权可以自动送审。

## VS Code F5 验收步骤

1. 在开发仓库按 F5 启动扩展开发宿主。把一个新的临时目录打开为可信工作区，在临时仓库配置测试身份，创建初始提交及 `v1.2`、`v1.10` 两个标签。为测试选择可用的主模型。
2. 在 KeepSeek 的审批模式中选一次「自动审批」，核对中英文权限提示。发送“逐条执行下列原始 argv 并报告实际输出”，附上前述两条 Git 命令。可立即切走或关闭 KeepSeek Webview，稍后重新打开。预期两个真实结果各一次，标签输出为 `v1.10`、`v1.2`，日志包含 HEAD 与标签装饰，Run Details 中均是 `host_policy`。两类 reviewer 均无调用，整个过程无审批按钮或 modal。
3. 发送一个任务，要求创建、修改、移动和删除临时文件，运行项目脚本、固定测试及清理生成目录。核对最终文件和退出码。再用普通内联 Node 代码写入带空格的中文文件名，核对独立 `auto_approval_review`、实际文件内容及原任务续跑。通过本地包测试安装，使用 `--offline` 并把缓存放在临时工作区。
4. 用单独的临时测试配置使自动 reviewer 不可用，重新提交需要 reviewer 的正常操作。预期零执行或仅运行独立且已获准的替代操作，最终显示原因和未完成项。使用临时外部文件测试缺少精确授权，不运行真实灾难命令。重新载入扩展时确认旧草稿、审批记录及执行许可不会重放。
5. 分别切到「请求审批」与「模型审批」。确认逐项按钮只在对应流程出现，模型审批的独立配置仍可用。以 Plan 模式发送“只提供方案”和“给出简短计划，然后实施”，分别确认只读交付和自动进入执行。后台验证修复只用临时项目检查测试通过与停止两条路径。

## 验证环境

回归使用生产 Provider、Runner、Store、SafeFileEditor 和 Executor 的对应入口。模型客户端以测试响应注入，Git、Node、Shell、Python 和项目文件操作在临时目录实际运行。危险样本只检验拒绝和零启动。实测平台为 macOS x86_64。VS Code CLI 为 1.145.0，使用隔离测试配置启动时出现 `task_name_for_pid` 权限错误，未得到扩展宿主测试结果。真实图形扩展宿主 F5、真实模型账号，以及 Windows 和 Linux 的进程行为需现场复核。

`bun run compile`、`bun run lint`、`bun run build:test` 和 `git diff --check` 通过。最终单进程全量回归共 977 项，976 项通过，0 项失败。1 项本地故障服务器用例因执行环境不允许绑定监听端口而跳过。并行试跑曾触发 10,000 条用量账本测试的计时阈值，最终单进程复验通过。
